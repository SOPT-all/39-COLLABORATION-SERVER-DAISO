# api-documentation Specification

## Purpose

팀원이 구현된 API의 입력과 응답을 정확히 확인하고 직접 호출할 수 있는 문서를 제공한다. 실제 HTTP 계약에 맞는 타입·필수값·예시·오류를 보여주며 개발 및 팀 배포 환경에서 같은 사용 흐름을 유지한다.

## Requirements

### Requirement: API 문서 제공
시스템은 SHALL 로컬과 팀 배포 환경에서 Swagger UI와 OpenAPI JSON을 제공하고 [API 계약](../../../docs/api/api-contract.md)의 구현된 API를 상품·매장 태그로 표시한다.

#### Scenario: 문서 접근
- **WHEN** 로컬 또는 팀 배포 서버의 문서 주소에 접근한다
- **THEN** 별도 인증 입력 없이 UI와 OpenAPI JSON을 조회할 수 있다

#### Scenario: API 탐색
- **WHEN** 문서를 처음 연다
- **THEN** 구현된 API를 도메인별로 찾을 수 있고 API 상세는 접혀 있으며 각 API를 열면 설명과 JSON 예시를 확인할 수 있다

### Requirement: 입력 계약 표현
시스템은 SHALL 실제 Java 수신 타입과 별개로 API 계약의 입력 위치·타입·필수 여부·범위·기본값을 문서에 표현한다.

#### Scenario: 상태 변경 본문
- **WHEN** 좋아요 또는 매장 찜 API의 본문을 확인한다
- **THEN** 필수 JSON 객체와 필수 boolean 필드가 표시되고 생략·null·문자열을 허용하는 것으로 안내하지 않는다

#### Scenario: 경로와 검색 조건
- **WHEN** ID·검색어·품절 제외 조건을 확인한다
- **THEN** 계약의 정수 범위, 선택 검색어, 품절 제외의 기본값과 허용값을 확인할 수 있다

### Requirement: 응답 계약 표현
시스템은 SHALL 성공 응답의 구체적인 데이터 구조와 실제 직렬화되는 필드·타입·필수 여부·표시 형식을 문서에 표현한다.

#### Scenario: 구체적인 성공 데이터
- **WHEN** 서로 다른 API의 성공 응답을 확인한다
- **THEN** 각 API의 실제 응답 구조를 확인할 수 있으며 제네릭 내부가 임의 객체로 축약되거나 다른 API의 구조로 합쳐지지 않는다

#### Scenario: 상품 정보와 빈 결과
- **WHEN** 상품 목록 또는 재고 조회 응답을 확인한다
- **THEN** 표시 문자열과 숫자·boolean이 구분되고 계약의 빈 배열 및 상단 상품 정보 유지 동작을 확인할 수 있다

#### Scenario: 재고 응답의 파생 정보
- **WHEN** 재고 조회의 매장 항목을 확인한다
- **THEN** 원본 거리와 계산된 표시 거리, 영업 상태, 공유 찜 상태가 실제 JSON 이름과 의미로 표현된다

### Requirement: 실패 응답 표현
시스템은 SHALL 공통 실패 구조를 재사용해 해당 API의 오류 조건·HTTP 상태·코드 예시를 제공한다.

#### Scenario: 오류 확인
- **WHEN** API의 실패 응답을 확인한다
- **THEN** 오류에 성공 data가 포함되지 않으며 재고 조회의 저장소 장애 등 해당 계약에 있는 오류를 확인할 수 있다

### Requirement: 문서에서 요청 실행
시스템은 SHALL 문서에서 사용자가 명시적으로 실행한 요청을 문서를 연 서버의 기존 API로 전달하며 기존 처리·검증·공유 상태 정책을 유지한다.

#### Scenario: 조회와 상태 변경 실행
- **WHEN** 사용자가 문서에서 조회 또는 상태 변경 요청을 실행한다
- **THEN** 같은 서버에서 API의 실제 응답을 확인하며 상태 변경 요청은 기존 공유 상태에 반영된다

#### Scenario: 기존 검증 유지
- **WHEN** 문서 설정 추가 후 잘못된 본문 또는 쿼리를 전달한다
- **THEN** 기존 계약의 거부 동작과 오류 응답이 유지된다
