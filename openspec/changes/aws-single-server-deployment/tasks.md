# Tasks

코드 구현과 인프라 준비의 진행 상태다. [설계](design.md)의 승인 묶음과 후보값을 따른다. 각 AWS·서버 변경은 실행 전에 해당 범위의 사용자 확인을 받아야 완료할 수 있다.

## 1. 서버 외부 검증과 SSM 배포 코드

- [x] 1.1 CI·CD를 Java 21·ARM64 빌드와 일회용 MySQL 전체 테스트로 정리한다. 로컬/Actions 검사에서 실패·필수 테스트 건너뜀 시 배포가 실행되지 않고, 이미지 manifest와 실제 실행으로 ARM64 호환을 확인한다.
- [x] 1.2 CD의 SSH·장기 AWS 키 의존을 제거하고 practice-production Environment의 main 전용 OIDC·지정 EC2 SSM 호출·명령 결과 대기를 구현한다. 잘못된 대상·명령 실패·시간 초과를 포함한 필요한 범위의 검사로 성공 오판과 비밀값 출력을 확인한다. 이 단계에서 실제 AWS 권한을 만들거나 기존 팀 Secrets를 덮어쓰지 않는다.
- [x] 1.3 scripts/deploy.sh에 고정 digest pull·배포 직렬화·DB 유지·상태 확인·직전 버전 기록을 구현한다. 격리된 컨테이너에서 pull 실패·최초 실패·앱 실패·DB 변경 여부에 따른 복구와 상태 보존을 검증한다. 사용법·실패 조건은 개발 가이드의 기존 배포 관련 설명에 통합한다.

## 2. 작은 서버의 실행 설정과 준비 코드

- [x] 2.1 docker-compose.prod.yml에 Spring·MySQL·내부 DB 네트워크·볼륨·메모리/스왑/로그 제한·재시작/health를 설정한다. Compose 해석과 실제 ARM64 컨테이너 기동으로 V1~V3·JPA validate·대표 API·볼륨 보존을 확인한다. 로컬 Compose 동작이 바뀌지 않았는지 함께 확인한다.
- [ ] 2.2 scripts/bootstrap-server.sh에 Docker·Compose·SSM Agent 준비와 1GiB 스왑·fstab·권한·재실행 시 중복 방지를 구현한다. 셸 검사와 버릴 수 있는 Linux 환경에서 최초/반복 실행을 확인하고, 파괴적 재초기화나 AWS 생성 명령이 없는지 검토한다. 승인받은 EC2에서만 실제 적용·재부팅 확인을 수행하며 개발 가이드에 준비·확인·종료 절차를 통합한다.

2.2의 스크립트 작성·셸 검사와 설치/시스템 명령을 모의한 Ubuntu 반복 실행 검사는 완료했다. 승인된 EC2에서 패키지 설치·스왑 1GiB 활성화·영구 설정·폴더 권한을 확인했다. 실제 재부팅 검증은 남아 있어 미완료로 유지한다. SSM 실패 처리는 모의 API, 앱 복구 분기는 Linux 내 모의 Docker로 검증했으며 실제 AWS 권한·실패 복구는 아래 통합 검증에 남아 있다.

## 3. 확인받은 AWS·GitHub 연결

- [x] 3.1 AWS 콘솔을 읽기 전용으로 확인하고 실제 AMI·서브넷·보안그룹 CIDR·CPU 모드·EBS·Elastic IP와 기본 비용을 사용자에게 제시한다. 기존 리소스와 구분하고 생성 전에 명시적 확인을 받은 범위를 확인한다.
- [ ] 3.2 OIDC 공급자·Actions 역할·EC2 역할의 신뢰/권한 및 main 제한을 제시하고 사용자 확인 후 생성·연결한다. 지정 서버의 SSM 온라인 상태, 허용한 호출과 다른 대상/브랜치의 거부를 확인한다. 새 서버·EBS·보안그룹·Elastic IP 역시 승인받은 옵션으로만 생성·연결하고 콘솔 값과 일치하는지 확인한다.
- [ ] 3.3 서버 초기 설정·비밀값 준비·레지스트리 인증·선택적 더미 적재 내용을 사용자에게 보여주고 확인 후 적용한다. 스왑 1GiB·권한·서비스 상태·이미지 pull·DB 포트 비공개를 확인한다. 비밀번호·토큰은 SSM 명령 기록이나 GitHub 로그로 전달하지 않으며 초기 데이터 반복 삽입이 없는지 확인한다.
- [x] 3.4 GitHub Environment와 대상 EC2·main 자동 실행 범위를 확인받아 연결한다. README의 기존 SSH Secrets 설명을 실제 SSM/OIDC 설정으로 교체하고 문서 링크·Git 비밀값 미포함을 확인한다. main 병합은 별도 사용자 요청과 팀 리뷰 절차에 따라 수행한다.

서버·고정 IP·EC2 역할·OIDC 공급자·배포 역할과 main 전용 Environment 및 변수 연결을 완료했다. SSM 대화형 접속은 확인했지만 Actions의 실제 역할 수임·명령 호출과 다른 대상/브랜치 거부 검증은 남아 있다. 개인 GHCR 게시 토큰 등록·첫 ARM64 이미지 게시·공개 전환과 로컬의 인증 없는 pull을 확인했다. [최초 게시 CI](https://github.com/SOPT-all/39-COLLABORATION-SERVER-DAISO/actions/runs/43565676180)에서 Java 테스트 156개(건너뜀 없음)와 배포 테스트 10개를 통과했다. 게시 전용 임시 workflow는 제거했다. 서버 `.env`는 사용자 입력 후 root:root·600 권한과 필수값 존재를 비밀값 출력 없이 확인했다. 실제 EC2의 이미지 pull·컨테이너 실행과 Actions의 AWS 호출 검증이 남아 있어 3.2·3.3은 미완료다.

## 4. 실제 배포 통합 검증

- [ ] 4.1 승인된 첫 배포를 수행하고 외부에서 health·Swagger UI·문서 JSON·조회·좋아요·찜을 확인한다. 상태 변경은 재조회로 확인하고 실제 EC2의 RSS·스왑·CPU·OOM·소량 동시 요청을 확인해 후보값을 조정한다. 내부 성공만으로 외부 접속 완료를 표시하지 않는다.
- [ ] 4.2 승인받은 재부팅·재배포로 스왑과 서비스 자동 재실행·상태 보존을 확인하고 실패 시 진단·이전 이미지 복구를 검증한다. main 자동 배포의 성공/실패 상태와 제안·명세·구현·API 계약을 대조하고 OpenSpec strict·하네스·문서 링크·diff 검사를 통과시킨다. 실제 검증하지 못한 항목은 완료 표시하지 않는다.

## Workflow follow-up

- 배포·외부 검증을 마친 동작만 현재 명세에 동기화하고 이 변경을 보관한다. 승인 대기·실제 EC2 미검증이 남으면 진행 중으로 유지한다.
- 실제 변경을 작업 단위별 한글 메시지로 커밋하고 배포 결과·비용/데이터 제약·남은 항목을 보고한다. 별도 작업 보고서는 만들지 않는다.
