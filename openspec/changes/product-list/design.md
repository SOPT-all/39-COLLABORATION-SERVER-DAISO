# Design

## Context

[제안](proposal.md)의 동기를 따른다. 기준은 머지된 dev(`24d699e`)와 좋아요 브랜치(`48b02d4`)다. `feat/12-product-list`는 후자에서 분기했으며 다른 미머지 브랜치의 코드·스키마는 전제하지 않는다.

현재 Product에는 V1의 상품 컬럼 매핑과 좋아요용 메서드만 있고 목록 조회는 없다. V1과 엔티티는 상품 이미지 null을 허용하며 ProductLikeIntegrationTest와 FlywayMigrationTests에도 이미지가 없는 상품 데이터가 있다. 개인·공유 DB의 실제 데이터는 확인하지 않았다.

HTTP 원본은 [API 계약](../../../docs/api/api-contract.md#6-상품-목록-조회), 동작은 [제안 명세](specs/product-list/spec.md)를 따른다. 계층·트랜잭션·검증은 [개발 가이드](../../../docs/development.md), 스키마 관리의 근거는 [ADR 0002](../../../docs/adr/0002-manage-schema-with-jpa-and-flyway.md)를 참고한다.

## Goals / Non-Goals

**Goals:** 기존 계층과 공통 응답을 재사용해 조회를 추가하고, 저장 타입과 표시 타입을 분리하며 이미지 필수 전환에서 기존 데이터와 테스트를 보존한다.

**Non-Goals:** 별도 조회 아키텍처·검색 엔진·캐시·검색 인덱스·새 의존성, 매장·재고 연동, 상품 등록·수정 API나 운영 데이터 적재 도구를 추가하지 않는다.

## Decisions

- 기존 ProductController에 선택 문자열 쿼리를 받는 GET을 추가한다. 검색어 하나를 위해 별도 요청 DTO·검증 계층을 만들지 않는다. ProductService의 읽기 전용 메서드에서 앞뒤 공백을 제거하고 Repository를 호출한다.
- 빈 검색어는 전체 조회, 나머지는 상품명 부분 일치 OR 품번 정확 일치로 조회하며 두 경우 모두 DB에서 ID 오름차순으로 정렬한다. 조건과 정렬은 Repository가 담당한다. 전체를 메모리에 읽어 검색하거나 추가 쿼리 프레임워크를 도입하지 않는다. 바인딩·LIKE 이스케이프로 검색어를 일반 문자로 처리하고 collation은 변경하지 않는다.
- Product에 필요한 getter를 추가하고 ProductListItemResponse·ProductListResponse를 둔다. 별도 projection 대신 이미 있는 단일 엔티티를 조회한다. 매장·재고를 조인하지 않으며 품번의 중복 방지 제약도 이번에 추가하지 않는다.
- 엔티티의 가격·리뷰 수는 int로 유지하고 응답 DTO를 만들 때 고정된 표시 규칙을 적용한다. 실행 환경의 기본 로케일에 따라 쉼표 표기가 달라지지 않게 하며 별도 범용 포맷터 계층은 만들지 않는다.
- 이미지는 실제 URL 또는 사용자가 준비한 대체 이미지 URL을 데이터에 저장한다. null을 허용하는 응답이나 서버의 임의 URL 치환 대신 필수 저장 제약을 맞춘다. 빈 문자열·가짜 URL을 보정값으로 넣거나 DB에 URL 기본값을 추가하지 않는다. 상품 이미지의 URL 제공·적재는 데이터 준비 단계에서 처리하며 원격 이미지 접근 검사·새 DB CHECK 제약은 추가하지 않는다.
- 현재 계약에 없는 검색어 길이 제한·새 400 오류·별도 검색 연산자를 추가하지 않는다. 성공과 서버 실패는 기존 ApiResponse·ErrorResponse·GlobalExceptionHandler를 사용한다.

## Risks / Trade-offs

- 전체 조회와 상품명 부분 일치 검색은 데이터가 커지면 비싸진다 → 적은 데이터라는 실습 전제에 맞추고 이번 범위에서 페이지네이션·검색 엔진을 도입하지 않는다.
- 대소문자·문자 비교는 DB 설정에 영향을 받는다 → 계약에 해당 기준을 명시하고 실제 검증 MySQL에서 결과를 확인한다.
- 좋아요 PR 리뷰로 선행 코드가 바뀔 수 있다 → 수정은 좋아요 브랜치에서 반영한 뒤 목록 브랜치에 이어받는다. 머지 후에는 아래 분기 기준을 사용해 목록 작업만 최신 dev에 옮기고 회귀 검증한다.
- 이미지 null 데이터가 남으면 필수 전환에 실패할 수 있다 → 적용 전에 누락 데이터와 사용자가 제공한 실제·대체 URL을 확인하고 기존 상품을 삭제하지 않고 보완한다. 이미지 필수 DB 제약이 URL의 유효성까지 보장하지는 않는다.

## Migration Plan

1. 개발 착수 전 최신 dev와 좋아요 PR 상태를 확인한다. 좋아요 머지 후에는 분기 기준 `48b02d4131eec268545997b6ea9287c3522edbd4` 이후의 목록 작업만 최신 dev 위로 옮긴다. 선행 작업을 추가로 이어받았다면 제외할 커밋 경계를 다시 확인한다. 목록 PR 대상은 dev로 한다.
2. 적용 대상 DB의 상품 이미지 누락을 확인하고 사용자가 제공한 실제 또는 대체 이미지 URL을 채운다. 상품 삭제·임의 URL 생성·개인 DB 초기화를 전제로 하지 않는다. URL이 준비되지 않았다면 해당 DB의 필수 전환은 보류한다.
3. 다음 가용 번호의 migration으로 `product.image_url`을 NOT NULL로 바꾸고 Product 매핑을 맞춘다. 현재 다음 번호는 V2지만 구현 시 최신 dev를 다시 확인한다. V1·매장 이미지·재고 컬럼은 변경하지 않는다.
4. 이미지가 빠진 기존 테스트 데이터를 보완한다. 빈 검증 DB와 V1 대표 데이터가 있는 검증 DB에서 순차 적용·데이터 보존·이미지 null 거부를 확인한다. 목록 조회와 기존 좋아요도 함께 검증한다.
5. 애플리케이션을 되돌려도 기존 상품 데이터와 이미지 필수 제약은 유지할 수 있다. 제약 완화가 필요하면 별도 후속 migration으로 검토하며 공유된 SQL을 되돌려 수정하지 않는다.

## Open Questions

- “이미지 없음” 이미지의 실제 URL과 상품 데이터의 전달 위치는 아직 제공되지 않았다. 사용자 제공값으로 데이터를 준비한다는 정책은 확정됐으며, 이 값은 구현 설계를 바꾸지 않지만 대상 DB의 이미지 필수 전환 전에는 필요하다.
