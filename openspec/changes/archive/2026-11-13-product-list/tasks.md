# Tasks

계획 검토 후 별도 구현 요청을 받은 다음 수행한다. HTTP 세부 계약은 [API 문서](../../../../docs/api/api-contract.md#6-상품-목록-조회), 전환 절차와 선행 PR 의존성은 [설계](design.md)를 따른다.

## 1. 상품 이미지 필수 전환

- [x] 1.1 대체 이미지 URL은 실제 데이터 준비 전에 제공받는 것으로 확인하고 전환 전제조건을 문서에 명시한다. 이번 검증은 별도 DB의 테스트 URL·대표 데이터로 수행하며 개인·공유 DB는 변경하지 않는다.
- [x] 1.2 후속 migration과 Product 매핑을 추가하고 이미지가 빠진 기존 테스트 데이터를 보완한다. 빈 MySQL의 전체 migration·JPA validate와 상품 이미지 null 저장 거부를 검증한다.
- [x] 1.3 V1 대표 데이터에 실제·대체 URL을 준비한 뒤 새 migration을 적용해 상품 ID·가격·리뷰 수·좋아요와 다른 테이블 데이터 보존을 확인한다.
- [x] 1.4 API 계약의 이미지 필수 전환 상태와 개발 가이드의 실제 migration·검증 안내를 구현 결과에 맞게 갱신하고 문서와 설정의 일치를 확인한다.

## 2. 상품 목록 조회

- [x] 2.1 기존 Repository·읽기 전용 Service에 전체·검색 조회와 ID 오름차순을 추가한다. MySQL 검증으로 빈 검색어·상품명 부분 일치·품번 정확 일치·앞자리 0·숫자 상품명·검색 특수문자·빈 결과·정렬·DB 문자 비교 기준을 확인한다.
- [x] 2.2 상품 getter와 목록 응답 DTO를 추가한다. HTTP 응답에서 전체 필드·타입, 가격 0·999·1000, 리뷰 수 0·999·1000·9999·10000의 표시, 실제·대체 이미지 URL의 원문 반환을 검증한다.
- [x] 2.3 기존 Controller에 GET을 연결한다. HTTP 검증으로 쿼리 생략·앞뒤 공백·빈 배열과 공통 성공·서버 실패 형식 및 내부 오류 정보 비노출을 확인한다.
- [x] 2.4 상품 좋아요 성공 후 목록 재조회에 저장값이 반영되는지 실제 HTTP·MySQL 연동으로 확인하고 기존 좋아요 회귀 테스트를 통과시킨다.
- [x] 2.5 API 계약의 구현 상태와 시나리오 링크, 개발 가이드의 목록 검증 안내를 실제 파일·실행 결과에 맞게 갱신한다.

## 3. 통합 확인

- [x] 3.1 머지된 dev와 현재 브랜치를 기준으로 빌드·테스트를 실행한다. 별도 MySQL 환경을 지정해 DB 테스트가 건너뛰어지지 않았는지와 매장 찜 회귀 결과까지 확인한다. 선행 PR이 이후 변경·머지되면 그 결과를 반영하고 회귀 검증한다.
- [x] 3.2 제안 시나리오와 API 계약·구현을 대조하고 OpenSpec strict 검증·문서 링크·git diff 검사를 통과시킨다.

## Workflow follow-up

- 완료·검증 후 현재 명세 동기화와 변경 archive를 수행하고 링크·명세 내용을 확인한다. 구현 전에는 수행하지 않는다.
- 작업 단위별 한글 커밋과 검증 결과를 보고한다. 좋아요 머지 후 목록 작업만 최신 dev 위로 정리하고 요청받은 범위에서 푸시·PR을 진행한다.
