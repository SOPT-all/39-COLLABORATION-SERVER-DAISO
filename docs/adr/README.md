# ADR (Architecture Decision Record)

프로젝트의 주요 기술·설계 결정과 그 이유를 기록합니다.
팀 전체에 영향을 주거나 변경 비용이 큰 결정을 대상으로 합니다.

## 기록 대상

- 패키지 구조와 계층별 책임
- 공통 API 응답 형식과 예외 처리 방식
- 데이터베이스와 데이터 접근 방식
- 인증·인가, 배포 등 팀이 함께 따라야 하는 설계

단순 설정 변경이나 작업 진행 상황은 이슈와 PR에 기록합니다.
확정되지 않은 결정은 `제안` 상태로 작성하고, 팀 합의 후 `채택`으로 변경합니다.

## 작성 규칙

- 위치: `docs/adr/`
- 파일명: `NNNN-kebab-case-title.md` (예: `0001-package-structure.md`)
- 번호는 `0001`부터 순서대로 사용합니다. 이미 사용한 번호는 재사용하지 않습니다.
- 한 문서에는 하나의 결정을 기록합니다.
- 배경과 선택 이유, 검토한 대안, 예상되는 장단점을 구체적으로 작성합니다.
- 관련 이슈와 PR이 있으면 링크를 남깁니다. 없으면 해당 항목을 생략합니다.
- 채택 후에는 기존 결정의 배경과 내용을 덮어쓰지 않습니다. 결정이 바뀌면 새 ADR을 작성하고 기존 문서를 `대체됨`으로 표시하며 새 문서를 연결합니다.
- 상태 변경, 관련 링크 추가, 오탈자 수정은 기존 문서에 반영할 수 있습니다.

## 상태

- **제안**: 논의 중이며 아직 합의되지 않은 결정
- **채택**: 팀이 합의한 결정
- **대체됨**: 새 ADR로 대체된 결정. 대체한 문서의 링크를 표시합니다.

## 템플릿

아래 내용을 새 파일에 복사해 작성합니다. 상태는 해당하는 값 하나만 남깁니다.

```markdown
# NNNN. 결정 제목

- 상태: 제안 | 채택 | 대체됨 (→ [새 ADR 제목](./NNNN-new-decision.md))
- 날짜: YYYY-MM-DD
- 관련 이슈: #이슈번호
- 관련 PR: #PR번호

## 배경

어떤 문제를 해결해야 하는지, 어떤 요구사항과 제약이 있는지 작성합니다.

## 결정

선택한 방식과 선택 이유를 작성합니다.
팀원이 구현할 때 따라야 할 구체적인 기준을 포함합니다.

## 대안

검토한 다른 방식과 선택하지 않은 이유를 작성합니다.

## 영향

기대하는 이점, 감수해야 할 단점과 제약을 작성합니다.
변경이 필요한 코드·API·설정·문서가 있다면 함께 기록합니다.
```
