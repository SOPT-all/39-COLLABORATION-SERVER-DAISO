# 0002. 로컬은 JPA 자동 반영, 배포 환경은 Flyway로 스키마 관리

- 상태: 제안
- 날짜: 2026-11-12

## 배경

초기 개발에서는 엔티티와 테이블 구조가 자주 바뀌므로 로컬 DB에 변경을 빠르게 반영할 필요가 있다. 반면 배포 환경에서는 데이터가 보존되어야 하고, 어떤 스키마 변경을 적용했는지 추적할 수 있어야 한다.

로컬에서 JPA 자동 반영만 확인하면 migration SQL 누락을 발견하지 못해 배포 환경에서 오류가 발생할 수 있다. 개발 편의와 배포 시 변경 이력 관리를 함께 확보하는 기준이 필요하다.

## 결정

| 환경 | JPA `ddl-auto` | Flyway | 목적 |
| --- | --- | --- | --- |
| 개인 로컬 개발 | `update` | 비활성화 | 엔티티 변경을 빠르게 DB에 반영 |
| 별도 migration 검증 DB | `validate` | 활성화 | SQL 적용 및 엔티티와 스키마의 일치 여부 확인 |
| 배포 환경 | `validate` | 활성화 | 버전이 있는 SQL로 스키마를 변경하고 매핑 검증 |

### 스키마 변경 절차

1. 엔티티를 변경하며 개인 로컬 DB에서 기능을 개발한다.
2. 같은 PR에 해당 스키마 변경을 담은 Flyway SQL을 함께 작성한다. JPA `update`는 migration 파일을 자동 생성하지 않는다.
3. PR을 올리기 전에 개인 개발 DB와 분리된 빈 MySQL 검증 DB에서 전체 migration을 순서대로 실행한다.
4. 검증 환경에서 JPA `validate`로 애플리케이션이 기동되는지 확인하고 변경 기능을 테스트한다.
5. 후속 migration은 직전 버전의 스키마와 대표 데이터를 가진 검증 DB에서도 적용해 데이터 보존과 변경 결과를 확인한다.
6. 배포 환경에서는 Flyway 적용 후 JPA `validate`로 엔티티 매핑을 검사한다. 검증 실패 시 배포 성공으로 처리하지 않는다.

배포 DB 스키마 변경의 기준은 migration SQL이다. JPA `validate`는 테이블을 생성하거나 수정하지 않으며, 검사 가능한 매핑 불일치를 감지하는 역할을 한다. 모든 인덱스·제약조건이나 데이터 변환의 정확성을 보장하지 않으므로 SQL과 변경 결과도 검토한다.

### Migration 파일 규칙

- 위치: `src/main/resources/db/migration/`
- 파일명: `V{번호}__{설명}.sql` (예: `V1__create_initial_schema.sql`)
- 초기 스키마는 첫 migration에 작성하고 이후 변경은 다음 번호의 파일로 추가한다.
- PR에 올라갔거나 팀에 공유되었거나 공유·배포 DB에 적용된 migration은 수정하지 않는다. 수정이 필요하면 새 버전을 추가한다.
- 개인 로컬 DB의 자동 반영 결과를 배포 DB에 직접 복사하지 않는다. 공유·배포 DB의 DDL 변경은 migration으로 남긴다.
- 같은 DB에서 JPA `update`와 Flyway가 동시에 스키마를 변경하지 않도록 프로파일별 설정을 분리한다.

Flyway를 아직 적용하지 않은 기존 공유·배포 DB가 있다면, 최초 도입 전에 기존 스키마와 초기 migration의 관계를 확인하고 baseline 또는 별도 전환 절차를 정한다. 기존 테이블에 초기 생성 SQL을 그대로 실행하지 않는다.

## 대안

| 대안 | 검토 결과 |
| --- | --- |
| 모든 환경에서 JPA `update` 사용 | 개발은 간편하지만 배포 DB 변경 이력과 데이터 변환 절차를 SQL로 검토·재현하기 어렵다. |
| 모든 환경에서 Flyway와 JPA `validate` 사용 | 환경 차이를 줄일 수 있지만 초기 엔티티 변경마다 migration을 적용해야 한다. 현재는 개인 로컬 개발의 편의를 위해 선택하지 않는다. |
| 배포 시 수동 DDL 실행 | 변경 누락과 환경 간 차이가 발생하기 쉽고 적용 이력을 코드와 함께 관리하기 어렵다. |

## 영향

- 개인 로컬 개발의 속도를 유지하면서 배포 DB 스키마 변경을 버전별로 추적할 수 있다.
- 엔티티와 migration SQL을 함께 관리해야 하며, 로컬 DB만으로는 배포 가능 여부를 판단할 수 없다.
- 빈 검증 DB에서의 최초 구성과 기존 스키마에서의 업그레이드를 모두 확인해야 한다. 검증 DB는 개발·공유·배포 DB와 분리한다.
- 로컬 DB에 JPA가 누적 반영한 결과와 migration으로 생성한 스키마가 다를 수 있으므로 별도 검증을 생략하지 않는다.
- Migration 검증을 자동화하려면 CI에 MySQL과 Flyway 검증 작업을 추가해야 한다. 현재 CI의 `bootJar` 검사만으로는 이를 검증할 수 없다.

### 구현 현황

- Flyway starter와 MySQL 지원 의존성을 추가했다.
- 로컬은 Flyway 비활성화와 JPA `update`, 운영은 Flyway 활성화와 JPA `validate`로 설정했다.
- 별도의 `migration` 프로파일은 명시적인 검증 DB 접속 정보를 요구하며 개발 DB로 자동 연결하지 않는다.
- 제공된 ERD를 기준으로 `product`, `store`, `store_inventory`의 V1 migration을 작성했다. 사용자 확인에 따라 ID 자동 생성과 상품·매장 재고 조합의 유일성을 적용했다.
- Migration 적용과 주요 제약조건을 확인하는 통합 테스트를 추가했다. 검증 DB 환경변수가 없으면 건너뛴다.

CI의 migration 자동 검증과 엔티티 구현 후 실제 매핑 검증은 후속 작업이다. 배포 DB에 실제 적용한 상태는 아니다. 팀 합의 후 상태를 `채택`으로 변경한다.
